When Language Models Write a Dictionary for Themselves

Drafted May 05, 2026 · Published May 30, 2026 Artificial Intelligence Source: arXiv:2605.01920
A new formal language, ACDL, precisely specifies how an LLM agent's prompt structure evolves across interaction turns.

We have a problem. Large language models are increasingly deployed as autonomous agents — systems that make a sequence of LLM calls, each feeding the model a mix of instructions, observations, and interaction history. The design of this input, and how it evolves turn by turn, determines whether the agent succeeds or fails. Yet describing that design is a mess: informal prose, ad hoc diagrams, or requiring someone to read through source code.

None of these capture precisely how a prompt evolves across interaction steps. None make it easy to compare two different context-construction strategies. And none are standardised enough to be used in a research paper without pages of prose.

Now, a team led by Noga Peleg Pelc at the Department of Computer Science and AI — working with Gal A. Kaminka and Yoav Goldberg — has proposed a remedy. Their preprint introduces the Agentic Context Description Language (arXiv:2605.01920), a formal language for specifying exactly how an LLM agent's context is structured and how it changes over time.

The engineering frontier you never knew existed

Most people who use ChatGPT or Claude think of prompting as a one-shot affair: you type a question, the model answers. But when you build an agent — a system that decides which tool to call, reflects on its own outputs, and loops through multiple reasoning steps — the prompt is no longer static. It grows. New observations get appended. Old reasoning traces are pruned or retained. Tools are injected at different positions in the message sequence. The order in which information appears fundamentally changes what the model does next.

This is what the researchers call context engineering, and it is a surprisingly subtle craft. Consider a simple ReAct loop — an agent that alternates between reasoning and tool use. Should the tool descriptions appear at the start of each turn, or only on the first turn? Should previous reasoning traces be included in full, or only the final answer? These design choices, invisible to the end user, can make the difference between an agent that solves a task reliably and one that spins its wheels.

ACDL makes these choices explicit. The language provides constructs for describing role message sequences, dynamic content that changes between turns, time-indexed references to previous interactions, and conditional or iterative structures within the prompt. The language can be written formally and then rendered into diagrams — diagrams that are precise enough to be checked against an implementation and clear enough to be sketched on a whiteboard.

A grammar for agent minds

The core intuition behind ACDL is simple: an LLM context is not a flat string. It has structure. There are multiple roles (user, assistant, tool). There are turns. There are blocks of content that repeat or change. ACDL defines a small set of primitives to capture this structure.

Think of it like a blueprint. Just as architects use standard symbols for walls, doors, and windows rather than describing each one in prose, ACDL gives researchers a standard notation for saying "the tool description appears here, the system prompt is static across all turns, and the interaction history includes only the last three reasoning steps." Unlike prose, this notation is precise enough that two researchers reading it will agree on what the agent does. Unlike code, it is readable without execution.

The preprint demonstrates ACDL by documenting several existing systems and their variants. One example contrasts three simple ReAct loop designs: a base implementation, one that omits reasoning traces from the action history, and one where tool descriptions appear at the last message rather than the first. The differences, which would require paragraphs of prose to describe, are immediately visible in the ACDL diagrams. The language also handles more complex systems: multi-turn multi-step agents, hierarchical tool calls, and systems with sub-agents that have their own contexts.

The team has released documentation and tooling at an associated website, so the community can start experimenting with ACDL immediately.

What gets measured gets described

Why does this matter? Because the field of LLM agents is growing explosively, and much of the progress depends on small engineering decisions that are currently communicated poorly. A paper might describe its agent as using "a standard ReAct loop" — but standard for whom? Different implementations differ in exactly the ways that ACDL captures. A result that works with one context structure may fail with another, and without a shared description language, researchers cannot meaningfully compare approaches.

ACDL does not solve the hard problems of agent design — it does not tell you which context structure is best for which task. But it provides something more fundamental: a way to be precise about what you are doing. In a field where papers increasingly depend on complex prompt engineering, that precision is a prerequisite for progress.

A standard waiting to grow

The preprint positions ACDL as a proposal for community adoption. The authors encourage its use both in day-to-day communication among researchers and in formal publications. Whether it catches on remains to be seen — standards in computer science have a mixed track record. But the need it addresses is real. As LLM agents proliferate, the lack of a shared vocabulary for describing their contexts will become an increasingly costly bottleneck.

Perhaps the most telling detail in the preprint is that the authors, having built ACDL, used it to describe systems they did not build themselves. They applied it to the DeepSeek agent, to OpenClaw, to OpenCode. This is not a language designed to make one specific system look good. It is a language designed to describe the design space itself.

For now, ACDL exists as a preprint and a set of tools. The question is whether the community picks it up — and whether it becomes, in time, as natural as describing a transformer architecture or a training dataset. A standard is not born. It is adopted.

This is a promising step toward that adoption.
