Regenerating Code That Refuses to Age

September 07, 2026 Artificial Intelligence Source: arXiv:2609.05364

What would happen to a software library if, every time its assumptions crumbled, we simply discarded the code and wrote it again from scratch? For most of computing history, the question belonged in a thought experiment for post-apocalyptic engineers. But a preprint (arXiv:2609.05364) from a team led by Suvinay Subramanian at Google DeepMind, with first author Samuel Kushnir and collaborators at MIT and Stanford, proposes that the absurdity now has an expiration date.

Machine-learning performance modeling is a uniquely hostile terrain for long-lived software. These tools estimate how much time, memory, or energy a model will consume before anyone pays for the hardware to run it. The problem is that the assumptions baked into today’s abstractions—the attention patterns, kernel shapes, routing strategies—are invalidated by tomorrow’s models and systems. Each successive model generation swaps one architectural assumption for another, and the performance model must follow or begin to lie.

The old answer was to keep patching the code, accumulating technical debt that compounds like interest on a loan that never matures. AI coding agents have changed the arithmetic. These are systems built on large language models that can open a repository, read a specification, write functions, and run tests. When regenerating an entire library costs less than paying down its accumulated debt, the rational choice flips: throw the implementation away and regenerate it from a better description.

The adjective “AI-native” matters here. Traditional tools treat AI as an assistant that suggests edits; SMART treats the learned agent as the fabrication process itself. That is a more radical shift than it may sound, because it moves the thing we must preserve from the artifact we execute to the artifact we read.

The library with almost no code

The SMART library follows this inverted economics to its conclusion. Its main branch contains almost no code. Instead, the repository is a directed acyclic graph of self-contained natural-language design documents. When a new model or system version appears, coding sub-agents regenerate the implementation from those documents alone. Every human change is a natural-language edit to a document—self-documenting by construction. The code is no longer the source of truth; it is an echo of the prose.

Think of the design docs as master recipes, and the coding agents as line cooks who do not improvise. A cook who follows the recipe precisely can reproduce the dish even if the kitchen is demolished overnight. But the analogy has a limit: cooking tolerates imprecision, while this library must reproduce numerical outputs to round-off precision. The agents are not improvising; they are following instructions.

This inversion is not entirely new. Formal methods have long generated code from mathematical specifications, but those specifications are themselves code-like and unforgiving. SMART replaces formal specs with natural-language documents and lets a learned model close the gap between prose and implementation. The gamble is that the model’s statistical facility with language is reliable enough to hold the bridge.

Worked examples as in-context demonstrations

Two ingredients make regeneration reliable. The first is a design-doc style built around step-by-step worked examples. Each document walks through a calculation as if tutoring a new engineer, and those worked examples double as in-context demonstrations for the generating agents.

In-context demonstrations are not fine-tuning. Rather, they are fully worked examples placed inside the prompt, from which a large language model infers the pattern it should follow. Here the examples are not generic programming puzzles; they are the exact reasoning the library needs, expressed in natural language and symbolic form. A document that shows how to compute the FLOPs of an attention layer, step by step, teaches the agent by demonstration rather than by description.

The second ingredient is a minimal, recursively defined operator intermediate representation. Each operator carries a symbolic cost expression—using SymPy, a symbolic mathematics library—so the system can reason about performance algebraically. The representation supports two evaluation paths: a fast analytical roll-up mode for large parameter sweeps, and a slower modulo-scheduling mode for fine-grained schedule studies. The same underlying representation can be evaluated quickly or slowly, depending on whether the question calls for a broad sweep or a precise schedule.

One can picture a small skeleton language: a handful of bones, each inscribed with a formula for its own cost, and rules for stacking those bones into larger structures. In this case, the picture is not a metaphor—it is a deliberate software architecture. The cost expressions are not approximations layered on top of the code; they are the primary substrate from which the code is generated.

What round-off precision actually certifies

As a reality check, the team targeted DeepSeek-V3 serving on a TPU pod slice—an important case from the DeepSeek-V3 Technical Report. Regenerated implementations reproduced hand-audited reference models to round-off precision. In the authors’ words, design docs—not code—can be the durable artifact for ML-systems co-design tools.

But what exactly does round-off precision certify? It depends on the granularity of the comparison. A question the paper leaves open is whether the regenerated model matches the reference only at the level of aggregated cost expressions, or also in the fine grain of routing dynamics and compression that determine real-world throughput. The abstract does not settle that question, and the credibility of the claim rests on the answer.

There is also no systematic comparison yet with established performance-modeling frameworks. The proof of concept demonstrates that the pipeline works on one hard target, not that it beats the tools researchers already use. A broader evaluation would need to show whether the document-first approach changes the ergonomics of model co-design, beyond simply moving where the source of truth lives.

A deeper risk lingers beneath the elegance. If the durable artifact is natural language, then any ambiguity in a design doc propagates into every regenerated implementation. A coding agent that misreads a clause could silently alter a cost model, and because the code is always regenerated, the usual safety net of reviewing the source becomes thinner. It is tempting to compare this to recompiling source code, but a deterministic compiler is not a learned model whose interpretation may drift from one generation to the next.

What this really challenges is the assumption that source code is the thing we must preserve. If a document can reliably regenerate correct code, then the artifact of record shifts from the implementation to the reasoning. Mathematicians have long preserved proofs over particular calculations; software has not. SMART is an attempt to import that older discipline into a field that changes faster than its own documentation.

The question is no longer whether AI can write code, but whether our design documents can become precise enough to serve as source code in their own right. Perhaps the most radical outcome of this experiment is not a new library, but a new definition of what software is.
