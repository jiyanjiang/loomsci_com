When 'Stop' Doesn't Mean Stop: The Enforcement Gap in AI Agents

Drafted August 11, 2026 · Published August 12, 2026 Artificial Intelligence Source: arXiv:2607.14166

But why assume that a “pause” button in a software framework actually pauses anything? Should we trust that clicking “cancel” on an AI agent’s task will reliably prevent its side effects from escaping into the world? A new preprint (arXiv:2607.14166) by independent researcher Sajjad Khan suggests the answer is a resounding no.

For years, we’ve been wiring language models to tools—databases, APIs, command lines—using frameworks that promise to keep them under control. They ship with control primitives: human‑approval gates, run cancellation, execution timeouts. The names imply a simple contract. While a run is paused, cancelled, or timed out, no gated side effect executes. Khan’s work demonstrates that this contract, known as barrier semantics, fails systematically across six widely‑used open‑source frameworks. The documented barrier has holes that neither the documentation nor the user interface reveals.

The Sibling Leak That Makes ‘Stop’ a Suggestion

The core failure is subtle enough to survive repeated releases. An approval gate works by intercepting a specific tool call—say, a request to send an email—and waiting for a human to approve or reject it. The gate suspends only the branch that triggered it. Meanwhile, a sibling branch—another concurrent task in the same run—continues executing. If that sibling also makes a side‑effecting tool call, nothing blocks it. The email goes out before the human has even seen the approval request, defeating rejection entirely.

This isn’t a deliberate backdoor; it’s a consequence of concurrent execution that the gate never sees. But the effect is indistinguishable from a privilege escalation. Khan uncovered the pattern using model‑free differential probes: automated test‑cases that compare the behavior of a gated run against the contract that the gate should enforce. The probes confirmed the sibling leak in every framework that ships a pre‑execution gate—five of six, spanning four execution models and two language runtimes. Khan also documented replay double‑execution, cancellation orphans, and timeout zombies, each a distinct way for a stopped run to leave real‑world effects behind.

The hazard is reachable. Frontier models produce the plan shape that triggers the leak in up to 14% of runs. In a controlled experiment, 215 of 1,200 runs using live models driving unmodified frameworks leaked a gated effect despite a pending or rejected approval—a perfect leak rate whenever the trigger pattern appeared. On naturalistic tasks the gap lies latent, because models seldom interleave writes aggressively. But once an injection induces the interleaving, the leak occurs deterministically. A corpus of public incident reports already echoes the replay and cancellation failures.

Why This Isn’t Just Another Race Condition

An important question sharpened by earlier work on time‑of‑check‑to‑time‑of‑use vulnerabilities in LLM agents (Lilienthal et al., arXiv:2508.17155) is whether the sibling leak is merely another instance of TOCTOU. The distinction matters. Typical TOCTOU attacks exploit a race between check and use along the same execution path. The sibling leak is structural: the gate never sees the dangerous path at all. It’s like a traffic officer who halts one lane but doesn’t know the other lane exists, so cars whizz through unmonitored. Unlike a real officer, though, the gate’s design explicitly assumes only a single lane—an assumption that no production framework challenges.

Khan’s repair, called SOUNDGATE, begins from a deceptively simple insight. If you cannot trust the framework’s internal machinery to mediate all side effects, move the mediation outside the framework entirely. SOUNDGATE is an environment‑external Rust gate through which every network egress must be admitted. This is the complete‑mediation contract: every side‑effecting path submits to a single, unforgiving checkpoint that enforces four properties: hold‑until‑decided (no effect before approval), reject‑cancels, dedup‑on‑replay, and fence‑on‑cancel. The principle is borrowed from operating‑system security, where a reference monitor must see every access to a resource. SOUNDGATE dispatches that contract through two kernel‑enforced network routes, ensuring that the gate’s logic—not the agent framework’s—becomes the ground truth.

The Gate That Keeps Its Promises

The admission core is mechanically verified. Khan modelled the gate's logic in TLA+, a specification language designed for concurrent systems, and let its model checker systematically explore the state space without finding a violation. The safety proof was then machine‑checked with TLA+’s proof system. To bridge the gap between the idealised model and the running Rust code, SOUNDGATE was subjected to differential conformance testing that compared the model's predictions against the deployed gate across millions of operations, yielding zero divergences. This is not a full end‑to‑end refinement proof, but the evidence that the implementation matches the verified model is strikingly consistent.

The cost of all this rigour is delightfully small. SOUNDGATE adds roughly a millisecond per write—about a hummingbird's wing flap—and sustains many thousands of admissions per second. Under that contract, it blocks every measured violation on all six frameworks while releasing legitimate effects. Gated episodes on realistic benchmarks complete with zero refusals.

The repair does, however, inherit a crucial boundary condition. The complete‑mediation contract is exactly that: a contract. If a tool can bypass the gate—by writing to a shared filesystem, using local inter‑process communication, or exploiting any channel not routed through SOUNDGATE—the guarantee dissolves. Khan is explicit about this scope. The verification covers the admission core’s logic, not the confinement of the entire tool runtime. This is the same tension navigated by earlier work on transactional tool use (Bindschaedler et al., Atomix, arXiv:2602.14849), which proposed atomic commit semantics for agent tool calls but also had to assume that all effects are captured by a transaction coordinator. Similarly, research on concurrency anomalies in multi‑agent systems (Khan, arXiv:2606.17182) demonstrated that verification must consider every interleaving of agent actions; SOUNDGATE’s TLA+ model does precisely that, proving the gate holds for any possible event ordering—provided every event enters the gate.

The Philosophy Beneath the Pause Button

What does this reveal about our relationship with artificial agents? We delegate them authority to book meetings, move money, and run experiments. Behind every delegation is an unspoken assumption: that we can stop them when needed. Khan’s findings expose a fault line between that assumption and the messy reality of concurrent software. The gap is not a bug in one framework; it is a widespread design pattern that treats “stop” as a suggestion rather than a command—a semantic gray zone where the user interface says one thing and the runtime does another.

The lesson extends beyond AI. In a world increasingly run by semi‑autonomous systems, the semantics of “stop” must be engineered as carefully as the actions themselves. This is not a question from a philosophy seminar; it is a concrete engineering challenge. Khan’s work is a blueprint for what it looks like to meet that challenge: not relying on good intentions, but building gates with formally proven contracts that survive the chaos of concurrent execution. The question it leaves us with is not whether we can make agents stop, but whether we are willing to do the hard work of ensuring that, when we say stop, something truly stops.
